# RadUI Run 2, WP0: server spike results (S2-1 to S2-10)

Date 2026-11-13. Radicale 3.9.0 with vobject 0.9.9 (the release RadUI targets), the PRODUCTION rights plugin
(`backend/plugin/radui_rights.py`), users and rights generated by the REAL backend (`backend/radui_admin`),
all on throwaway loopback ports 15400-15409 under `.throwaway/run2/` (removed after every script). Names are
placeholders (alice, bob, agent-1, example.org). Nothing here touches the live Radicale, nginx, fail2ban or systemd.

Layout of every spike (`common.py: standard_stack`): `alice` administrator owning the address book `contacts`
and the calendar `cal-work`; `bob` holds a **readwrite** grant on both and owns `bob-book` / `bob-cal` (a
non-administrator owner); `agent-1` holds a **read** grant on both. Grants are made through the backend API
(`PUT /grants`), so the rights file is the generated one.

Run: `spike/run2/server/run_all.sh [OUTPUT_DIR]` (about 6 minutes, S2-10 takes 4 of them; refuses to start with
less than 2 GB available). Each script prints `PASS` / `FAIL` / `INFO` lines with the observed evidence.
`expect` lines (PASS/FAIL) test an assumption of the plan or a safe behaviour the code will rely on; `INFO` lines
are observations. Two full runs gave identical PASS/FAIL/INFO verdicts for every line (timings and ETags in the
evidence text vary, the verdict never does).

**PASS.** Owner, rw grantee and r grantee receive byte-identical bodies, status 200.

| | Address book | Calendar |
|---|---|---|

## S2-2 Group cards through PUT -> GET

**PASS (nothing lost).** RFC 6350 (`KIND:group`, `MEMBER:urn:uuid:`, VERSION 4.0) and the Apple form
(`X-ADDRESSBOOKSERVER-KIND:group` / `-MEMBER`, VERSION 3.0), each with 50 members, come back byte-identical:
same MEMBER lines, same order (also reversed order, 0 members, 1 member), no reordering. MEMBER values that are
not `urn:uuid:` (`mailto:`, `https://`, `urn:uid:`, a bare word, an upper-case UUID) are stored verbatim in both
forms. Adding one member by a PUT with If-Match is 204 and the rest of the card is unchanged. The only
normalisation is the generic one of S2-3 (refolding at 75 characters: a hand-folded 3-segment MEMBER line came
back as two segments, same logical line).

## S2-3 Fidelity per vCard shape (extended)

43 cases (vCard 3.0 and 4.0), each PUT then GET, compared at five levels: byte-identical, same-lines (folding
only), reordered, semantic (case / parameter order / TYPE merging), different.

**Radicale 3.9 re-serialises every PUT through vobject.** Observed rules (all deterministic, all stable: a
re-PUT of the GET text returns the same bytes for all 43 cases, and rows of one property name keep their order):

1. Property order: `VERSION`, `PRODID`, `UID` first, then alphabetical by property name (group prefix ignored),
   stable for equal names (`TEL`, `EMAIL`, `ADR` rows keep their relative order). Sent TEL,EMAIL,ORG,TITLE after
   FN,N came back `VERSION UID EMAIL FN N ORG TEL TITLE`.
2. Property names are upper-cased, **including grouped ones**: `item1.X-ABLabel` returns as `item1.X-ABLABEL`,
   `item2.X-ABLabel:_$!<HomePage>!$_` as `item2.X-ABLABEL`. The group prefix itself keeps its case (`Item1.`).
3. Parameter names are upper-cased (`type=` -> `TYPE=`); TYPE values keep their case.
4. Repeated parameters are merged: `TEL;TYPE=work;TYPE=voice` returns `TEL;TYPE=work,voice`. The comma form
   `TYPE=work,voice` and `TYPE="work,voice"` (4.0) come back as sent.
5. Parameter order is normalised: `TEL;VALUE=uri;TYPE=cell` returns `TEL;TYPE=cell;VALUE=uri`.
6. Long lines are re-folded at 75 characters (an unfolded 330-character NOTE is folded, a folded one stays).
7. LF-only input is stored with CRLF.

**Preserved byte for byte** (inside the rules above): escaped commas and semicolons in N, ORG, ADR, NOTE; ADR
with unescaped commas (multi-valued component); `CATEGORIES:Family\,Friends,Work` and repeated CATEGORIES; BDAY
in all forms (`19840412`, `1984-04-12`, `--0412`, `VALUE=text:circa 1800`, Apple `X-APPLE-OMIT-YEAR=1604` with
`1604-04-12`) on 3.0 and 4.0; `ANNIVERSARY` (full and year-less) on 4.0; `item1.X-ABDATE;type=pref` with
`X-ABLabel:_$!<Anniversary>!$_` and `X-ANNIVERSARY` on 3.0; `PREF=1` / `PREF=2` rows (4.0) and two rows with
`TYPE=CELL,pref` / `TYPE=WORK,pref` (3.0); `TEL;VALUE=uri:tel:...` on both versions; an N with a multi-valued
given name (`Jane,Mary`); unicode and emoji; `X-` properties with parameters.

**FAIL (2): multi-value `NICKNAME` is truncated by the server on PUT.** `NICKNAME:Jay,Janie` is stored as
`NICKNAME:Jay` (4.0 and 3.0). The stored file is already truncated, so this is a silent server-side data loss
(vobject). `NICKNAME:Jay\,Janie` (one nickname containing a comma) survives. This hits ANY PUT of a card that
contains an unescaped multi-value NICKNAME, even when the user edits something else (a phone number): the
card loses its second nickname without any client being able to prevent it after the PUT. Only NICKNAME showed
this among the multi-valued properties tested (CATEGORIES, N, ADR, ORG are fine).

**What a write verification (normalised projection) must tolerate** (29 of 43 cases are not byte-identical: 27
benign, 2 NICKNAME): property reordering (rule 1); upper-cased property names including `X-ABLABEL` and grouped names
(rule 2); upper-cased parameter names (3); TYPE token lists as a SET, order and repeated-vs-comma form
irrelevant (4); parameter order (5); refolding (6); CRLF vs LF (7). It must NOT tolerate: any change of a value,
a missing row, a changed group-to-row association (`itemN` pairing), or a NICKNAME that lost a comma-separated
value. The projection used in `common.py: projection()` (names and parameter names upper-cased, repeated
parameters merged, parameter values lower-cased and sorted, value untouched, whole thing a sorted multiset)
returns "equal" for all 41 other cases and "different" for exactly the two NICKNAME cases.

## S2-4 ETag of the PUT response

**PASS.** For cards and events, as owner and as rw grantee, for a 201 (create) and a 204 (replace): the PUT
response carries an `ETag` header, equal to the ETag of the next GET, of PROPFIND Depth 1 and Depth 0, of
`sync-collection` and of an `addressbook-multiget` / `calendar-multiget`. The ETag of a 204 differs from the
one before. The PUT ETag can be used as `If-Match` immediately (204 each time). Form: quoted, strong, 64 hex
digits (a hash of the STORED text, so the ETag describes what Radicale re-serialised, not what was sent).
An identical re-PUT returns 204 with the same ETag. The collection GET has an ETag of its own that changes
when an item is added.

## S2-5 Collection management over DAV

**PASS** (20 PASS, 0 FAIL).

* MKCOL on an existing address book name: **405** `The method is not allowed on the requested resource.` (text
  body). MKCALENDAR on an existing calendar name: **409** `<error xmlns="DAV:"><resource-must-be-null/></error>`.
  Other kind on an existing name: the same two codes. The existing collection is untouched.
* A name ending in `~` (calendar or book): **400** `Bad Request`. A `~` inside a name (`til~de`) is fine (201).
  For items: `item~.vcf` 201, `item.vcf~` 400.
* MKCOL by a grantee (rw or r) under the owner's space: 403. By an account with `ownSpace=false`: 403. (The
  legacy-imported `agent-1` has an own space and can create: `ownSpace` is an account attribute, not implied by
  `type=bot`.)
* DELETE of a collection, as the administrator-owner (alice) and as a non-administrator owner (bob), book and
  calendar alike: with the ETag of the collection taken BEFORE an item was added (stale) **412**
  `Precondition failed.` and the collection stays; with the fresh collection ETag (from a collection GET) 200
  with a DAV multistatus body; without If-Match 200. DELETE of a missing collection 404.
* **rw grantee DELETE of the collection itself: 403** (collection still there); r grantee 403. A PUT on the
  collection URL by an rw grantee 403, PROPPATCH (rename) by an rw grantee 403 (the generated grant carries the
  letter `l`), PROPPATCH by the owner 207. So collection edit and delete are owner-only (plan D-R2-5 holds).
* Read-only grantee, every write: PUT new item, PUT replace, DELETE item, DELETE collection, PROPPATCH, MOVE,
  PUT on the collection URL, MKCOL inside, MKCALENDAR in the owner's space: all **403**; nothing changed.
  An rw grantee can PUT a new item (201) and DELETE an item (200).

## S2-6 PUT shapes

**1 FAIL, rest PASS.**

* **A vCard without UID is REFUSED, not completed: 400 `Bad Request`**, nothing stored (3.0, 4.0 and a group
  card; also a 2.1 card without UID). A UID-less file that was dropped into the storage directory behind
  Radicale's back is invisible: GET 404, absent from the collection GET and from listings; a PUT over it without
  UID is 400. So **a contact without a UID cannot exist on the server** and the client must generate the UID of
  every new card (import included).
* Same UID under two different names in one book: second PUT **409** `<CR:no-uid-conflict/>`. Changing the UID
  of an existing item under the same name: 409. A UID different from the file name: accepted and kept
  (GET `named-x.vcf` shows `UID:uid-y`; GET `uid-y.vcf` is 404, nothing resolves a UID to a name). UIDs with
  `/`, a space, `urn:uuid:` or non-ASCII characters are accepted (201).
* **vCard 2.1 is accepted and silently damaged** (201, stored as `VERSION:2.1`): `TEL;HOME;VOICE:+1...` comes back
  as `TEL:+1...` (the bare type parameters are lost), `N:Format;Old` as `N:Format;Old;;;`, a quoted-printable
  `FN;ENCODING=QUOTED-PRINTABLE;CHARSET=UTF-8:Caf=C3=A9` as `FN;CHARSET=UTF-8:Café` (decoded, ENCODING removed).
  The client-side refusal of 2.1 (Q3) is the only guard and is justified.
* Two cards in one file at one name: **400**, nothing stored (the import must split `.vcf` files itself).
* **FAIL: a non-UTF-8 body is accepted (201) and decoded as ISO-8859-1.** A Windows-1252 file with `e-acute` and
  the euro sign: the e-acute survives, the euro sign comes back as U+0080. The client-side UTF-8-only refusal
  (Q3) is the only guard.
* A UTF-8 BOM before `BEGIN:VCARD`: 400 (the import must strip it). Empty body, plain text, a VCALENDAR in an
  address book: 400. A wrong `Content-Type` (`application/octet-stream`): accepted, the type is not checked.
  A 200-character file name, a percent-encoded name: 201; a sub-path (`sub/dir.vcf`): 409. A 3 MB card: 201 (the
  1 MB per-item import limit is a client rule).

## S2-7 `sync-collection`

**PASS** (14 PASS, 0 FAIL), address books and calendars identical.

* Token form `http://radicale.org/ns/sync/<64 hex>`. Replacing one item (204) is reported ONCE as a `200` entry
  and the token changes. A re-PUT of identical text leaves the token unchanged and reports nothing. Delete one
  item and create another between two syncs: `c -> 404`, `d -> 200`. An item deleted and recreated under the
  same name between two syncs is reported as `200` (no 404).
* **Collection deleted and recreated under the same name: the old token is REFUSED with 403 and a
  `<valid-sync-token/>` DAV error body** (also when the recreated collection is empty, when it holds other items
  under the same names, and when it holds the identical items again). While the collection does not exist the
  REPORT is 404. A fresh empty-token sync of the recreated collection returns its items and a new token. So no
  stale items can survive an incremental client.
* The same 403 `valid-sync-token` answers an unknown or a malformed token. A real permission failure is also a
  403 (a plain-text body): a client must look at the body to tell them apart. A token taken by alice works for
  agent-1 (it describes the collection, not the user).
* Read-only grantee: empty token 207, old token 403, as for the owner.

## S2-9 Conflict primitives

**PASS** (26 PASS, 0 FAIL), books and calendars identical.

* Two clients (alice, bob; same ETag on read): A `If-Match: e0` -> 204. B `If-Match: e0` -> **412**, headers
  `content-length content-type date server` (**no ETag**), body `Precondition failed.` (`text/plain; charset=utf-8`).
  B's GET afterwards returns A's text and A's ETag; B's retry with it -> 204.
* The `If-Match` value must be the quoted ETag EXACTLY as served: the unquoted hex form, a weak form
  (`W/"..."`), a list (`"deadbeef", "<current>"`) and garbage all give **412** even though the current ETag is
  in them. Only `*` (204) and the verbatim quoted ETag work.
* `If-None-Match: *` on an existing name -> 412 (same body); on a new name -> 201. PUT without any precondition
  on an existing name overwrites silently (204): the UI must always send If-Match.
* `If-Match` on a name that does not exist -> **412** (not 404), nothing created; a PUT with a stale If-Match
  after the item was deleted -> 412. So 412 on a PUT is ambiguous (changed elsewhere vs deleted elsewhere) and the
  client has to GET to tell (GET -> 404 = deleted).
* DELETE with a stale If-Match -> 412 and the item stays; with the current ETag -> 200 (DAV multistatus, text/xml);
  DELETE of an already deleted item -> **404** with or without If-Match (`The requested resource could not be
  found.`); GET of it -> 404.
* Two simultaneous PUTs with the same If-Match: exactly one 204, one 412 (the check is atomic).
* A read-only grantee gets 403 before any precondition is looked at.
* An item deleted and recreated with identical text gets the same ETag again (content-derived: a stale ETag can
  match a recreated identical item; harmless).

## Implications for the plan

Confirmed:

* **D-R2-15 export, S2-1.** `GET` on the collection works for owner, rw and r grantee, returns the whole
  book (`text/vcard`, plain concatenation) or one merged calendar (`text/calendar`, VTIMEZONEs de-duplicated).
  The plan's fallback (client-side concatenation, merging `.ics` and de-duplicating VTIMEZONEs) is NOT needed;
  `getCollectionText` is a plain GET. 2,000 contacts export in 0.4 s (2.3 MB).
* **D-R2-12 groups, S2-2.** Both group forms survive PUT -> GET intact, 50 members, order kept, non-UUID MEMBERs
  kept verbatim. The "pass unknown members through unchanged" rule is safe.
* **D-R2-7 re-GET after every PUT, S2-4.** The PUT response ETag equals every later ETag (GET, PROPFIND, sync,
  multiget) for 201 and 204, so the store can take the ETag from the PUT response. The extra GET is still
  needed, but only to verify the TEXT (S2-3), not to learn the ETag.
* **D-R2-17 collection create, S2-5.** 405 (MKCOL) / 409 (MKCALENDAR) on an existing name and 400 for a name
  ending in `~` match the plan's "mapped from 405/409 to a field error" and `names.py`; edit and delete of a
  collection are owner-only, an rw grantee gets 403 on DELETE, PROPPATCH and PUT of the collection; a read-only
  grantee gets 403 on every write.
* **Section 3 concurrency (412 handling).** Stale PUT/DELETE -> 412, `If-None-Match: *` on an existing name ->
  412, deleted item -> 404 on GET and DELETE, first writer wins atomically. "GET theirs; 404 opens the
  deleted-elsewhere variant" is exactly what the server supports.
* **D6 sync.** `sync-collection` reports replaced items once, deleted items as 404, and refuses the old token of
  a deleted-and-recreated collection, so no stale items can survive.
* **S2-10 scale.** A 2,000-contact book loads in about 1.3 s of server time (sync 0.5 s + one multiget 0.4 s
  + two bcrypt floors), a single multiget of all cards is fine (2.8 MB), and 32 connections give no 5xx or drop.

Contradicted, or needs a change:

1. **K3 / M1 NICKNAME is worse than "show only the first value" (S2-3).** The SERVER truncates
   `NICKNAME:a,b` to `a` on every PUT of the card, even when the user edits only a phone number. Emitting the
   nickname only when edited does not help: the unedited property line is part of the PUT text. The fidelity
   guard / write path must detect an unescaped comma in an outgoing NICKNAME and either refuse the write
   (read-only card, "export this contact") or ask for an explicit confirmation naming the lost value; the write
   verification will flag it after the fact but cannot repair it. (`NICKNAME:a\,b` survives, but it changes the
   meaning to one nickname with a comma.) Add a fixture with a multi-value NICKNAME to the WP3 vcf fixtures and
   to the WP5 no-op corpus expectations (the corpus no-op test is about the model, not the server: the
   integration test of WP9 is where this shows).
2. **M8 projection: the list of tolerated differences is long (S2-3).** The projection must make property
   order irrelevant, compare property and parameter names case-insensitively (including the grouped
   `item1.X-ABLABEL`), treat TYPE as a set (repeated = comma list), ignore parameter order and refolding. In the
   MODEL too: after the first PUT every `X-ABLabel` is `X-ABLABEL` on the server, so label lookups must be
   case-insensitive (the model/DAV agent should check `vcard.js`). Values, row counts, `itemN` pairing and
   group members are never allowed to differ.
3. **Q11 / M10 UID-less contacts, `<key>` fallback (S2-6).** Radicale refuses a card without UID (400) and hides
   a UID-less file in storage, so "a contact without a UID" cannot occur over DAV. The refusal branch of "add to
   group" and the "key = file name when the UID is missing" fallback are unreachable in practice (harmless, can
   stay as defence). The import must GENERATE a UID for UID-less cards (plan D-R2-16 already says so) and the
   server will not do it for the UI.
4. **M10 "excluded from exports" vs D-R2-15 (S2-1, S2-2).** The whole-collection GET includes group cards.
   Either the book export is raw (group cards included, as Apple Contacts does; simplest and the 4.0/3.0 mix in
   one file is the server's) or the UI must filter, which means client-side splitting instead of
   `getCollectionText`. The plan has to pick one; the spike supports raw export. The `.ics` export carries a
   rewritten `PRODID` (pyvobject) and `X-WR-CALNAME`, not the original PRODIDs.
5. **Sync token refusal is a 403 (S2-7).** The old token of a recreated collection (and any unknown or malformed
   token) answers 403 with a `valid-sync-token` XML body, not 410/412. The D5 handling must key on the body (or
   on "403 on a REPORT that worked before"), never on the status alone: a revoked grant is also a 403 (plain
   text). Treat `valid-sync-token` as "do a full resync".
6. **If-Match must be sent verbatim (S2-9).** Unquoted, weak and list forms all produce 412 even when the ETag
   is right; a client that normalises the ETag would turn every save into a false conflict. Keep the quoted
   string as served. Also: 412 on PUT does not tell "changed" from "deleted"; the GET decides (plan 3.2 already
   does this). PUT without a precondition overwrites silently, so every PUT must carry If-Match or
   If-None-Match.
7. **Import guards (S2-6).** The server accepts vCard 2.1 and a non-UTF-8 body and damages them silently (2.1:
   bare TYPE parameters dropped, quoted-printable decoded; non-UTF-8: decoded as ISO-8859-1, e.g. the euro sign
   becomes U+0080). The client-side refusals of Q3 are therefore the ONLY guard; keep them mandatory, test
   them with a euro-sign file, and also strip a UTF-8 BOM (Radicale answers 400 for `BOM + BEGIN:VCARD`). Two
   cards in one file are refused (400), so `importplan` must split. A duplicate UID under another name is 409
   (`no-uid-conflict`): the "skip" and "keep both" policies need the UID set of the target book, which the
   multiget gives.
8. **Cold item cache (S2-10), affects WP10 and G-snap.** Cards that reach the storage by file copy cost about 12 ms
   each on the FIRST read (2,000 cards: 22-35 s for whichever request comes first, 61-86 s if other requests run at the same time),
   afterwards 0.4-0.5 s. m14 seeds the 2,000 perf cards by filesystem copy: the perf scenario must make one
   warm-up read (any request that lists the book) BEFORE the timed load, with a first-request budget of at
   least 120 s, so that the timed numbers describe a warm cache, not a restore. The same holds for G-snap data
   and for a production restore from an archive. The rendered nginx template gives the Radicale location
   `proxy_read_timeout 300s`, which covers about 20,000 cold cards; `src/js/dav/client.js` has no fetch
   timeout today, and any timeout WP4 adds to reads must leave room for this first read (or the UI shows a
   false "network error" on the first open of a restored book).
9. **Per-request cost at bcrypt 12 (S2-10).** Every request costs 0.32-0.44 s of wall time even when it reads
   nothing; a save is PUT + verification GET, about 0.7 s. The plan's "3 requests at a time" import therefore
   tops out near 8-9 requests per second (derived: 3 in flight x 0.35 s each; 5,000 PUTs: about 10 minutes), and the import verification
   by one multiget per chunk instead of one GET per item (M8) is necessary, not optional. Plan the progress text
   for minutes, not seconds. No ordering problem was seen with 32 connections.
10. **ADDENDUM B/M3 conflict flow (S2-9).** Nothing in the server contradicts it; note that the 412 carries
    no current ETag, so the "theirs" GET after a 412 is mandatory (the ETag of that GET becomes the new If-Match).
