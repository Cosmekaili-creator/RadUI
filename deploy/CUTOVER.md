# Cutover: from a hand-written rights file to RadUI

This is the procedure for switching an existing Radicale installation (static `users` and
`rights` files) to the files generated by the RadUI admin backend. It is written with
placeholders: `example.org`, `radui`, `radicale`, `/etc/radui`, `/var/lib/radui`, `/opt/radui`,
`/var/www/radui-ui`. Use the values from your own `deploy.local/vars.env` (which is git-ignored);
keep your real paths and notes there, not in this file.

Nothing here is scripted blindly. `deploy/install-backend.sh` covers only steps 1 and 2; every
step after that changes a running service and is done by hand, with a check after each step.
Roll back with [ROLLBACK.md](ROLLBACK.md); if something is already broken, start at
[RECOVERY.md](RECOVERY.md).

## Who and when

* **Operator** with a root shell on the host (does every step).
* **Account owner**, the person who will be the first admin: reviews the equivalence report
  (step 3), decides go / no-go, and checks that a real calendar client still syncs (step 9).
* Plan for **45 to 60 minutes**, in a quiet period. The only service interruption is the single
  Radicale restart in step 7: expect **1 to 3 seconds** of refused connections or 502 answers.
  Clients retry by themselves. Nothing else restarts Radicale: later rights changes are picked up
  by the plugin without a restart.
* Do not start while another change to Radicale, nginx or fail2ban is in progress.

## Preconditions (all must be true)

1. The release you are about to install passed its tests (`make test`, round-trip and integration
   suites) and you have its tree on the host (the directory with `backend/`, `deploy/`, `tools/`,
   `src/`).
2. Supported Radicale: a 3.9 series release. Check the installed version
   (`<radicale python> -c 'import radicale; print(radicale.VERSION)'`). Another series: read
   [docs/upgrading-radicale.md](../docs/upgrading-radicale.md) first.
3. Radicale authenticates with `type = htpasswd` and bcrypt hashes, and the Radicale unit can be
   given a drop-in (it is a systemd unit, not a container with a fixed command line).
4. Disk space for the backups of step 4 (the collections tarball is the big one), and a copy of
   everything on **another machine** if the collections are not already backed up elsewhere.
5. `deploy.local/vars.env` exists (copy of `deploy/vars.example.env`), every value reviewed, and
   `python3 tools/render-deploy.py --vars deploy.local/vars.env --out deploy.local/rendered`
   succeeds. Read the rendered files once.
6. You know the login of the legacy admin account that will become the first RadUI admin.
7. **A monitor alert is in place** on the backend health answer: `ok: false` or `active: false`
   for more than a few minutes must reach a human (any monitor that can poll
   `http://127.0.0.1:5233/ui/api/health` from the host will do; RadUI ships none). Radicale falls
   back to the last-known-good rights copy (fail-static) when the main file is unusable, and
   only this alert, plus the backend's self-heal timer, tells you. Test the alert once by
   stopping the backend briefly after step 5. This is a prerequisite of **Gate C** (the live
   cutover), not an optional extra.
8. **`max_connections` is chosen and recorded.** The measured recommendation is 32
   (`docs/testing.md`, `RADICALE_MAX_CONNECTIONS` in `deploy.local/vars.env`; the example file
   still shows a lower value). Write the value you set, and why, in your change record.
9. **The equivalence check is fresh.** Re-run the dry-run import (step 3) on **fresh copies** of
   the legacy files taken on the day of the cutover, not on an earlier copy, and have the owner
   review that report again (an earlier dry run is not evidence for today's data).
10. **The real built-in web UI has been checked against the strict CSP.** Before the nginx change
   of step 10, load `/.web/` through the rendered configuration on a spare vhost or port (or
   with a throwaway Radicale) and confirm it works under the policy in
   [docs/SECURITY-MODEL.md](../docs/SECURITY-MODEL.md); if it needs inline script or style, do
   not weaken the policy for the whole site: give `/.web/` its own location, or switch the
   built-in UI off (`[web] type = none`).
11. Nobody has the Radicale built-in web UI open on the data you are about to change; it keeps
   working afterwards, but you want a quiet system for the checks.

## Step 1. Install the backend (H1, H2: Radicale untouched)

```
deploy/install-backend.sh --vars deploy.local/vars.env             # dry run: read the plan
deploy/install-backend.sh --vars deploy.local/vars.env --apply     # as root
```

It creates the `radui` user and group, the directories (state `0700`, managed directory
`2750 radui:radicale`), the backend code under `/opt/radui/backend`, the plugin file under
`/opt/radui/plugin`, `/etc/radui/config.toml` and the systemd unit. It does not enable or start
the unit and does not touch Radicale, nginx or fail2ban. Every replaced file is first copied to
`<archive dir>/<thing>.before-radui-<YYYYMMDD>` (mode 600).

Check: `systemd-analyze verify /etc/systemd/system/radui-admin.service` prints nothing;
`systemd-analyze security radui-admin.service` shows a low exposure.

## Step 2. Deploy the web app and the nginx snippets (not yet active)

```
tools/deploy-static.sh --dest /var/www/radui-ui --init                      # dry run: what would be copied
tools/deploy-static.sh --dest /var/www/radui-ui --init --backup-dir /var/backups/radui --apply
install -m 0644 deploy.local/rendered/nginx/radui-security-headers.inc \
                deploy.local/rendered/nginx/radui-proxy-headers.inc \
                deploy.local/rendered/nginx/radui-locations.conf  /etc/nginx/snippets/
install -m 0644 deploy.local/rendered/nginx/radui-http.conf /etc/nginx/conf.d/
```

`tools/deploy-static.sh` builds the service-worker file list `sw-manifest.js` (in a temporary copy,
never in `src/`), backs up an existing `/var/www/radui-ui` (a new directory on a first install has
nothing to back up), copies `sw-manifest.js`, `sw.js` and `index.html` **last**, keeps an existing
`config.json` and checks every SHA-256 afterwards; it prints the rollback command. Do not copy the app
with a bare `rsync --delete` or `cp -r`: a half-copied tree makes the worker install fail on every
client. The snippets do nothing until the vhost includes them (step 10); the rendered
`radui-locations.conf` must contain the `location = /ui/sw-manifest.js` block (`Cache-Control: no-cache`).
Later app versions: [docs/UPGRADE-UI.md](../docs/UPGRADE-UI.md).

## Step 3. Import the legacy files, dry run first (H3a). Gate: the owner reviews the report

As root, give the service user private copies of the legacy files (never point the import at the
live files):

```
install -d -m 0700 -o radui -g radui /var/lib/radui/import
install -m 0600 -o radui -g radui /path/to/legacy/users  /var/lib/radui/import/users
install -m 0600 -o radui -g radui /path/to/legacy/rights /var/lib/radui/import/rights
```

Dry run, as the service user:

```
sudo -u radui radui-admin-cli import --admin <legacy admin login> \
     --users /var/lib/radui/import/users --rights /var/lib/radui/import/rights \
     --report /var/lib/radui/import/report.txt --dry-run
```

If the legacy rules use wildcards for collection names, also pass `--collections <json file>`
(`{"owner": ["collection", ...]}`) so the importer knows the names.

**Review `report.txt` with the account owner.** It compares, for every login and path, what the
old rules allowed with what the generated rules will allow, and classifies each difference:

* `expected_tightening`: something the new layout deliberately no longer allows (explicit delete,
  overwrite and PROPPATCH letters, deleting a principal, a legacy admin rule that matched
  arbitrary top-level names or the generation path);
* `expected_loosening`: something new (the admin's access to everything, own principal, root
  discovery, the generation probe path);
* `unexplained`: must be **zero**. The command refuses to import otherwise (exit code 4).

Read every tightening and loosening line. Then run the same command **without** `--dry-run`: it
writes generation 1 into `/var/lib/radui` and `/etc/radui/managed` (the generated `users` and
`rights`) and keeps the baseline. Radicale does not read those files yet. Then:

```
sudo -u radui radui-admin-cli check-radicale        # expect: OK radicale <version>, <n> probes, users compared
sudo -u radui radui-admin-cli show                  # accounts, grants
rm -r /var/lib/radui/import                         # the copies are no longer needed
```

## Step 4. Backups before the cutover

Names follow `<thing>.before-radui-<YYYYMMDD>` in the archive directory, mode 600, root-owned:

```
D=$(date +%Y%m%d); A=/var/backups/radui          # your ARCHIVE_DIR
install -d -m 0700 $A
install -m 0600 /etc/radicale/config        $A/radicale-config.before-radui-$D
install -m 0600 /etc/radicale/users         $A/radicale-users.before-radui-$D
install -m 0600 /etc/radicale/rights        $A/radicale-rights.before-radui-$D
( umask 077; tar -C /var/lib -cf $A/radicale-collections.before-radui-$D.tar radicale/collections )
# the Radicale unit and its existing drop-ins, if any:
( umask 077; tar -C /etc/systemd/system -cf $A/radicale-unit.before-radui-$D.tar \
    radicale.service $(ls -d radicale.service.d 2>/dev/null) )
```

Adjust the paths to your layout. Verify the tarball lists its contents (`tar -tf ... | head`). The
original `users` and `rights` files are never modified by RadUI; they are the rollback.

## Step 5. Start the backend and look at it

```
systemctl enable --now radui-admin
systemctl status radui-admin --no-pager
journalctl -u radui-admin -n 20 --no-pager           # a "startup" audit line, reconcile:ok
curl -s -H 'Host: example.org' http://127.0.0.1:5233/ui/api/health
```

The health answer has `"modelOk": true`. `"active"` is still `false`: Radicale is not using the
generated rights yet (the probe sees a 401). That is the expected state at this step (the monitor alert of precondition 7 may fire until step 7; silence it for this window only).

## Step 6. Prepare the Radicale change (still no restart)

1. Install the drop-in from `deploy.local/rendered/systemd/radicale-radui.conf` as
   `/etc/systemd/system/radicale.service.d/radui.conf` (`PYTHONPATH` and `PrivateTmp=yes`;
   `PrivateTmp` is required by the plugin). Merge, do not overwrite, an existing `PYTHONPATH`.
2. Edit Radicale's configuration as `deploy.local/rendered/radicale/config-snippet.ini` shows
   (`[auth]` points at the generated `users`, `[rights] type = radui_rights` with the generated
   `rights`, `permit_delete_collection = False`, `permit_overwrite_collection = False`).
3. `systemctl daemon-reload` (this does not restart Radicale).
4. Checks, before the restart:

```
# the plugin imports as the Radicale user, with the drop-in's PYTHONPATH
sudo -u radicale env PYTHONPATH=/opt/radui/plugin <radicale python> -c 'import radui_rights; print("plugin imports")'
sudo -u radui radui-admin-cli check-radicale            # the files pass Radicale's own engine
# rehearsal: the NEW configuration on a spare loopback port and an empty storage, as the Radicale user
sudo -u radicale env PYTHONPATH=/opt/radui/plugin <radicale binary> --config /etc/radicale/config \
     --server-hosts 127.0.0.1:15999 --storage-filesystem-folder /tmp/radui-rehearsal &
sleep 3; curl -s -o /dev/null -w '%{http_code}\n' -X PROPFIND http://127.0.0.1:15999/    # 401
kill %1; rm -r /tmp/radui-rehearsal
```

`check-radicale` must end with `users compared` (the report's `users_checked=True`: the users
file was loaded by Radicale's own htpasswd code and compared with the model). `users parsed
only` means that comparison was skipped (Radicale's internals changed, or the file could not be
loaded): treat it as a **failure** and do not restart Radicale until it is explained. The Radicale
user must also be able to read the managed files: the plugin import above and the rehearsal below
run as that user and prove it.

The rehearsal must log one WARNING line starting `radui_rights: active, hot-reload enabled` and no
CRITICAL or ERROR line. Any failure here: stop, do not restart; undo with ROLLBACK B (nothing has
restarted yet, so only the edited files and the drop-in need to go back).

## Step 7. Restart Radicale (the only interruption)

```
systemctl restart radicale
journalctl -u radicale -n 30 --no-pager
```

Expect the WARNING line `radui_rights: active, hot-reload enabled ...` and nothing at ERROR or
CRITICAL. If Radicale does not come up within 10 seconds, go straight to ROLLBACK A or B.

## Step 8. Verify, immediately

```
curl -s -H 'Host: example.org' http://127.0.0.1:5233/ui/api/health     # "active": true
curl -s -o /dev/null -w '%{http_code}\n' -X PROPFIND http://127.0.0.1:5232/    # 401 without credentials
```

`active: true` means the backend's probe saw the new generation answer 404 on its secret path,
i.e. Radicale runs the generated rights. Then the **smoke test**, which creates a temporary bot
account, checks its rights (own principal 207, someone else's 403, create and delete its own
calendar), deletes the account and checks that its login is refused:

```
read -rs RADUI_SMOKE_ADMIN_PASSWORD; export RADUI_SMOKE_ADMIN_PASSWORD       # the admin's password
sudo --preserve-env=RADUI_SMOKE_ADMIN_PASSWORD -u radui \
     radui-admin-cli smoke --radicale-url http://127.0.0.1:5232 --admin-login <admin login>
unset RADUI_SMOKE_ADMIN_PASSWORD
```

The smoke test leaves an empty principal directory for its temporary login and that login
tombstoned; nobody can delete a principal over DAV, so a root user may remove the empty directory
from the storage later (or leave it).

## Step 9. Client checks (the owner, on a real device)

* The calendar and contacts apps that already sync (a phone with DAVx5 or the native apps, a
  desktop client) still sync, and a new item appears on the server and on a second device.
* A user with a grant (an ordinary bot or person account) can still reach exactly the collections
  it could before: compare with the equivalence report.
* The Radicale built-in web UI, if it was used, still works.

If any check fails: ROLLBACK A (keeps RadUI's changes) or B (back to the original files).

## Step 10. nginx: UI, API and the address headers

Only after steps 7 to 9 passed. This step and step 11 are a **pair** and are done in the same
window: the `X-Forwarded-For` overwrite and the fail2ban jail are never shipped separately.

1. Back up the vhost: `install -m 0600 <vhost file> $A/vhost.before-radui-$D`.
2. Edit the vhost to include the snippets, as `deploy.local/rendered/nginx/radui-vhost-example.conf`
   shows: the security-headers include, then `include .../radui-locations.conf;`. The proxy header
   include replaces any `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for` line in the
   old `location /` (the new `/` location is in `radui-locations.conf`; remove the old one).
3. `nginx -t` then `systemctl reload nginx`.
4. Check: `curl -sI https://example.org/ui/` (200, the CSP and all security headers);
   `curl -sI https://example.org/ui/sw.js` and `curl -sI https://example.org/ui/sw-manifest.js` (both
   `Cache-Control: no-cache`);
   `curl -s --resolve example.org:443:127.0.0.1 https://example.org/ui/api/health` from the host
   (200) and from anywhere else (403); a CalDAV `PROPFIND /` still answers 401 without credentials;
   the built-in UI under `/.web/` (checked against the strict CSP beforehand, precondition 10; repeat
   it here on the live vhost; if it breaks and you need it, give `/.web/` its own location, see the
   comment in `radui-locations.conf`).
5. The backend honours `X-Real-IP` only from a peer in `trusted_proxies` (default: loopback). If
   nginx connects from loopback nothing needs changing; otherwise add its address to
   `trusted_proxies` in `/etc/radui/config.toml` and restart `radui-admin`. Check that the audit
   line of a deliberate failed login shows the client address, not `127.0.0.1`.
6. Open `https://example.org/ui/` and sign in as the admin.

## Step 11. fail2ban jail (pair with step 10)

```
install -m 0644 deploy/fail2ban/radui-radicale-auth.conf /etc/fail2ban/filter.d/
install -m 0644 deploy.local/rendered/fail2ban/radui-radicale-auth.jail.conf /etc/fail2ban/jail.d/radui-radicale-auth.conf
fail2ban-client -t                                  # configuration test
systemctl reload fail2ban
fail2ban-client status radui-radicale-auth
```

Put your own static addresses in `F2B_IGNOREIP` first. Verify the filter on the real journal
without banning: `fail2ban-regex systemd-journal[journalmatch="_SYSTEMD_UNIT=radicale.service"] radui-radicale-auth`
after one deliberate failed login from a test client (the line must show the client address, not
`127.0.0.1`). If it shows `127.0.0.1`, the nginx overwrite is not live: do not leave the jail on.

## Step 12. Housekeeping

Record the change (date, versions, what was backed up where). Keep the backups at least until the
change has run for two weeks without problems, then delete them according to your retention rules.
Remove temporary files, `systemctl reset-failed` any unit you stopped on purpose, and check disk
space.

## Stop conditions

Stop and roll back when: the equivalence report has an unexplained line; `check-radicale` fails;
Radicale does not start; `active` stays `false` after the restart; the monitor alert of precondition 7 does not fire in its test; the smoke test fails; a client
that worked before cannot sync. Do not "fix forward" at the moment of an outage: roll back first.
